## 1. Context

Réglages grew card by card, and every card that needed to write something grew its own « Enregistrer »
button next to the one the page already has in its action bar. On `/parametres` the « Assurance
annulation (Neat) » card carries **three** of them — credentials, selection, mapping
([`SettingsNeatSection.jsx`](../client/src/components/SettingsNeatSection.jsx)) — while
[`PageActionBar`](../client/src/components/PageActionBar.js) shows a fourth at the top of the same
screen that saves everything else. Nothing tells the operator which button owns which field, and
CLAUDE.md §7 has said since the beginning that the bar is *the* place for page-level actions.

The same page asks for values it could work out on its own. The SMTP card asks for a port **and** for a
security mode, when the two are the same answer twice: 587 goes with STARTTLS, 465 with implicit TLS.

Réglages → Paiements has the reverse problem: one connection spread over two cards. « Application
Qonto » holds the credentials, its own Save and its own test button; « Connexion bancaire (Qonto) »
holds a badge, four summary lines and two more buttons — one of which, « Enregistrer le webhook », is a
manual step for something the code can do by itself. That button exists because the webhook subscription
was set up by hand during the production switch of 2026-09-15: the operator invented a secret, pasted it
into a field, clicked the button, and Qonto has been delivering payment events ever since. None of that
has to be an operator's job, and the secret should never have been on screen at all — it was displayed in
clear while being typed, which is why the switch had to pause for it.

That same switch surfaced one more defect. Once the production credentials were saved, the authorisation
was granted at Qonto and the browser came back to Réglages → Paiements — and the page announced a
connection failure. The connection was fine. `qontoCallback` stores the tokens and redirects without
ever calling Qonto again, so the page still showed the state recorded *before* the repair; pressing
« Tester la connexion » turned everything green without changing a single setting. GuestFlow had the
answer and did not go and get it.

Finally, the reconciliation poll still ticks every 15 minutes
([`scheduledTasks.js`](../server/src/scheduledTasks.js)), a cadence chosen when the webhook did not
exist yet. Since `specs/public-online-payment.md` §3bis the webhook is the primary signal and the guest's
own success page triggers an on-demand check, so the cron is a safety net running 96 times a day for
something that has to catch an outage, not a payment.

## 2. Goal

Réglages asks for less, saves in one place, and sets up the Qonto webhook by itself — so that connecting
GuestFlow to Qonto never again requires inventing a secret, pressing a registration button, or guessing
which « Enregistrer » writes which field.

## 3. Functional rules

**One Save per page**

1. On a settings page, the action bar's Save is the only control that writes settings. No card carries
   its own « Enregistrer », and the bar's Save becomes available as soon as *any* card on the page holds
   an unsaved change.
2. Saving writes every block that changed and only those: an untouched block is not posted, so a save
   never re-sends values the operator did not touch.
3. When one block is refused, the blocks already written stay written, the refused values stay in the
   form, and the reason is shown against the fields concerned — the page never silently drops what the
   operator typed.
4. The unsaved-changes guard that protects a page on leaving counts the cards' own changes too, not just
   the page form's.

**Less to fill in**

5. The SMTP port is not entered any more. The server derives it from the chosen security — 587 for
   STARTTLS, 465 for implicit TLS — and writes it on every save of the email settings. A port sent by a
   client is ignored.
6. The webhook secret is never displayed, never asked for and never entered. It is generated by the
   server, stored encrypted, and has no field anywhere in the interface.

**The webhook subscribes itself**

7. GuestFlow makes sure by itself that Qonto is subscribed to payment-link events at the address
   GuestFlow answers on — no button, no operator action.
8. It never creates a second subscription: when Qonto already has one pointing at that address,
   GuestFlow adopts it as it is and keeps using the secret it already holds, without touching anything
   at Qonto.
9. A subscription is created only when Qonto has none at that address, and a secret is generated only
   when none is stored — 32 random bytes in hexadecimal, saved encrypted like every other Qonto secret.
10. The check costs nothing when the recorded subscription still matches the current public address:
    no Qonto call at all. It reaches Qonto only when that record is missing or stale.
11. The check runs after each successful Qonto authorisation and at the start of each reconciliation
    pass. A failure is recorded like any other Qonto failure, is shown in Réglages → Paiements, and
    never interrupts the pass or the authorisation.

**One card for the bank connection**

12. Réglages → Paiements shows a single « Connexion bancaire » card, in this order: the redirect URI to
    declare at Qonto, the credentials, the date of the last verification, then the actions. The Qonto
    hosts GuestFlow calls, the mode, the credentials-present line and the provider line are not shown:
    the diagnosis already names whichever of them is the problem.
13. The card offers exactly two actions, side by side: « Connexion » then « Test ». Both are
    unavailable while the page holds an unsaved change, and hovering one says to save first.
14. A successful Qonto authorisation is followed, server-side and before the operator is sent back, by
    a real connection test whose outcome becomes the recorded state. The page therefore opens on what is
    true now, never on the failure that preceded the repair. A test that fails does not undo the
    authorisation: the tokens are kept and the diagnosis is shown instead of a bare « échec ».

**Edge cases:**

- An installation whose stored SMTP port is neither 587 nor 465 → it keeps that port until the email
  settings are saved again, at which point rule 5 aligns it. Nothing is rewritten by the migration.
- Qonto has a subscription at our address but its secret is not the one we hold (created by someone
  else, or lost) → rule 8 adopts it and deliveries keep failing signature verification. GuestFlow cannot
  read a subscription's secret back, so the repair is to delete the subscription in Qonto and let rule 9
  create a fresh one. Named in the diagnosis, out of scope for automatic repair.
- The public address changes → the recorded callback no longer matches, rule 10 falls through to a
  Qonto call, rule 8 finds no subscription at the new address and rule 9 creates one. The old one stays
  at Qonto, harmless: it points at an address GuestFlow no longer answers on.
- Qonto is unreachable when the check runs → rule 11 records the failure and the pass continues; the
  next pass tries again.
- A card is dirty and the operator presses Save while another card's request is still in flight → the
  bar's Save is busy for the whole page, so a second press is impossible.
- Nothing is dirty → Save stays disabled, exactly as today.

## 4. Architecture

> **Fat backend, thin frontend.** The port derivation (rule 5), the secret generation, the decision to
> adopt or create a subscription (rules 7–11) are all server-side. The client only stops showing fields
> and buttons, and hands one Save down to the cards that used to have their own.

### 4.1 Server side (`server/src/`)

| Layer | File | T/C | Responsibility in this change |
|---|---|---|---|
| `routes/` | `payments.js` | T | Drops `POST /qonto/webhook/register` (rule 7 removes its reason to exist) |
| `controllers/` | `paymentsController.js` | T | Drops `registerQontoWebhook`; the OAuth callback verifies the connection (rule 14) then triggers the webhook check (rule 11) |
| `controllers/` | `settingsController.js` | T | Drops `port` from the SMTP field map and derives `smtpPort` from `secure` (rule 5) |
| `models/` | `settingsModel.js` | T | Reads/writes the subscription record; stores a generated webhook secret (rules 9, 10) |
| `utils/` | `qontoWebhookRegistrar.js` | C | `ensureWebhookSubscription()` — the whole of rules 7–11, pure of HTTP, client injected |
| `utils/` | `settingsValidation.js` | T | `smtpPortForSecure(secure)` — the pure derivation of rule 5; `validateSmtpPort` stays for the stored value |
| `utils/` | `paymentPollSchedule.js` | C | `resolvePaymentPollTickMs(env)` — the tick of `payment-polling-fair-use` rule 11 |
| `scheduledTasks.js` | `scheduledTasks.js` | T | Poll tick 15 min → 8 h; calls the registrar at the start of a pass (rule 11) |
| `database.js` | `database.js` | T | Idempotent block adding the two subscription columns |

**Notes:**
- `qontoWebhookRegistrar.js` takes its Qonto client and its settings model as arguments, so its six
  branches (recorded-and-matching, recorded-and-stale, adopt, create, no-public-url, failure) are unit
  tested without a network or a database.
- No new dependency: `crypto.randomBytes(32).toString('hex')` generates the secret.
- The registrar is called through the existing `withQonto` choke point, so a failure is recorded and
  surfaced by `specs/qonto-settings-in-app.md` rule 12 with no extra plumbing.

### 4.2 Client side (`client/src/`)

| Layer | File | T/C | Responsibility in this change |
|---|---|---|---|
| `pages/` | `SettingsPage.jsx` | T | Bar Save also saves the Neat card; tracks its dirty state for the bar and the guard (rules 1–4) |
| `pages/` | `PaymentsSettingsPage.jsx` | T | Owns the credentials draft; bar Save writes credentials + timings; drops the old status card and the webhook action |
| `components/` | `SettingsNeatSection.jsx` | T | Loses its three Save buttons; reports dirtiness and exposes `save()` to the page (rules 1–3) |
| `components/` | `SettingsSmtpSection.jsx` | T | Loses the Port field; the security select carries the port in its helper (rule 5) |
| `components/` | `QontoConnectionCard.jsx` | C | Renamed from `QontoApplicationCard.jsx`: the single « Connexion bancaire » card of rules 12–13 |
| `components/` | `QontoApplicationCard.jsx` | — | Removed (renamed) |
| `api.js` | `api.js` | T | Drops `registerQontoWebhook` |

`SettingsNeatSection` keeps its own data and its own three endpoints — moving them into
`SettingsPage`'s form draft would put a second feature's shape inside the general settings payload. It
publishes two things upward instead: `onDirtyChange(bool)` so the bar knows, and an imperative
`save()` through a ref so the bar can write. That is the smallest seam that satisfies rule 1 without
merging two data models.

**Component reuse declaration:**

| Category | Components | Notes |
|---|---|---|
| **Consumed (existing generic)** | `PageActionBar`, `StatusBadge`, `SummaryItem`, `MaskedTextField`, `HelpedTextField`, `ErrorAlert`, `ConfirmDialog` | All pre-existing. The merged card is a composition of them. |
| **Created (new generic)** | — | None. |
| **Specific (kept feature-local)** | `QontoConnectionCard` | Every field names a Qonto concept (staging token, redirect URI, client id); no second page can consume it. |

### 4.3 API contract

| Method | Endpoint | Request body | Response | Notes |
|---|---|---|---|---|
| ~~POST~~ | ~~`/api/payments/qonto/webhook/register`~~ | — | — | **Removed** (rule 7). No consumer outside this repository; the WordPress plugin never called it. |
| PUT | `/api/settings` | `smtp: { …, secure }` | unchanged | `smtp.port` is ignored if sent; the stored port follows `secure` (rule 5) |
| GET | `/api/settings` | — | unchanged | Still returns `smtp.port` — the mailer reads it; the interface no longer shows it |
| PUT | `/api/payments/qonto/credentials` | unchanged | unchanged | `webhookSecret` is still accepted (the registrar writes through it) but no longer sent by the interface |

Auth is unchanged everywhere: `/api/payments/**` and `/api/settings` keep their session guard.

## 5. Data model

Two additive `app_settings` columns, added by an idempotent block in `server/src/database.js` next to
the existing `qonto*` block:

| Column | Type | Default | Encrypted | Role |
|---|---|---|---|---|
| `qontoWebhookSubscriptionId` | TEXT | `''` | no | Id of the subscription GuestFlow created or adopted (rules 8–10) |
| `qontoWebhookCallbackUrl` | TEXT | `''` | no | Address that subscription points at, so rule 10 can skip the Qonto call |

Neither is a secret: an id and a public URL. `qontoWebhookSecretEncrypted` already exists and keeps its
encryption.

- **Default for existing rows:** empty. Empty means « nothing recorded », so the first check after the
  upgrade reaches Qonto once, finds the subscription created by hand on 2026-09-15, adopts it (rule 8)
  and records its id. From then on, rule 10 makes the check free.
- **Backfill:** none.

**Data impact:** additive only. No existing value is rewritten — in particular the stored webhook secret
is left exactly as it is, which is what keeps the production subscription working. The SMTP port column
is not migrated either (rule 5 acts on save).

- Title « Connexion bancaire », `variant="sectionHeader"` like every other card on the page — the old
  `StatusCard` rendered it in another style, which is the format problem this fixes. The verified-state
  badge stays, at the right of the title.
- Gone from the screen: « Serveurs appelés », « Mode », « Identifiants », « Provider de liens »,
  « Secret du webhook », « Enregistrer », « Enregistrer le webhook ».
- « Connexion » replaces « Connecter Qonto » / « Reconnecter Qonto » — one label whatever the state,
  because the button does the same thing either way. « Test » replaces « Tester la connexion ».
- Both actions are `disabled` while the page is dirty, wrapped in a `<span>` so the tooltip still fires:
  « Enregistre d'abord tes modifications. » When the credentials are missing, « Connexion » stays
  disabled with its existing reason.
- The page's `PageActionBar title="Paiements" backTo="/settings"` keeps its Save, which now writes the
  credentials **and** the timings.

**Réglages** — « Assurance annulation (Neat) » loses « Enregistrer », « Enregistrer la sélection » and
« Enregistrer le mappage ». « Tester la connexion » and « Charger les canaux de vente » stay: they read,
they do not write. The card's unsaved changes light up the bar's Save and the « Modifications non
enregistrées » subtitle, exactly like the rest of the page.

**Réglages → Envoi d'emails** — the Port field disappears. The security select keeps its two options,
« STARTTLS (port 587) » and « TLS implicite (port 465) », and its helper becomes « Le port est déduit :
587 en STARTTLS, 465 en TLS implicite. »

**Responsive:** unchanged patterns. The merged card is one column on `xs`, two from `md` (the existing
grid). The two actions stack vertically and go full width on `xs`
(`flexDirection: { xs: 'column', sm: 'row' }`), side by side from `sm`. Removing three buttons from the
Neat card and one field from the SMTP card shortens both on mobile.

**Sticky action bar:** both pages keep the bar they have. `/parametres` — title « Paramètres », subtitle
= the unsaved-changes caption, Save + Cancel. `/parametres/paiements` — title « Paiements », `backTo`
`/settings`, Save only. No new action is added to either bar.

## 8. Out of scope

- Rotating the Qonto webhook secret, or deleting a stale subscription at Qonto. GuestFlow cannot read a
  subscription's secret back, so a rotation means deleting the subscription in Qonto first — an operator
  action on Qonto's side, deliberately left there.
- The other self-contained cards (Google Calendar, Système et mises à jour): they have no Save to move,
  only actions, which the bar is not meant to hold.
- SMTP ports other than 587 and 465. An installation needing 25 or 2525 would need the field back; none
  does.
- Anything about the reconciliation cadence beyond the tick itself — the per-link decay and the back-off
  stay exactly as `specs/payment-polling-fair-use.md` defines them.
- The `PUBLIC_API_KEY`, Google and SMTP credentials, which still live in `.env.local`.
