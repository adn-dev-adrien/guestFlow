## 1. Context

Reservations are identified today only by their internal `id` (an opaque auto-increment). Devis
(`kind = 'devis'`) already carry a human-readable `devisNumber` in the `AAAA-MM-###` format, generated by
`generateDevisNumber()` ([database.js:637](../server/src/database.js#L637)) and stored with a partial
unique index `ux_reservations_devisNumber`. Reservations (`kind = 'reservation'`) have **no equivalent** —
there is nothing to quote on the phone, write on a contract, or search by.

There is also **no reservation search** anywhere in the app. The `GET /reservations` list endpoint filters
only by `propertyId` / `clientId` / date range ([reservationsModel.js:88](../server/src/models/reservationsModel.js#L88));
to open a fiche today the operator must scroll the calendar or the dashboard. A name/number lookup pattern
already exists server-side for emails (`/emails/eligible-reservations?q=` matches `firstName || ' ' || lastName`),
which we can mirror.

The operator wants, on the reservation fiche, a **human-readable reservation number** (auto-generated,
overridable), and a **search box** to jump straight to a fiche by typing a number, a name, a first name,
"last + first", or an email — with results shown live as characters are typed.

## 2. Goal

Every reservation gets a readable, unique **numéro de réservation** (auto-generated `AAAAMM###`, editable
by the operator on the fiche). From the **search box in the top bar** (global, reachable on every page), the
operator can **type a number, a name, a first name, or "nom prénom"** and see matching reservations appear
live, then click one to open its fiche.
The number is also **recalled to the guest in the J-7 and J-2 reminder emails**.

## 3. Functional rules

### Reservation number

1. A new column `reservations.reservationNumber` (TEXT) holds a human-readable identifier for
   `kind = 'reservation'` rows. Format: **`AAAAMM###`** — year + month + a 3-digit counter reset each month,
   **no separators** (e.g. `202606001`). Independent sequence from `devisNumber`.
   _(The number was originally `AAAA-MM-###`; the separators were dropped — a one-shot migration reformats
   the original-format values, see §5.)_
2. The number is **generated server-side at reservation creation** (`generateReservationNumber()`), scanning
   existing `reservationNumber` values for the current `AAAAMM` prefix and incrementing the max.
3. The number is **overridable**: the operator can edit it on the fiche. On save, a non-empty value is taken
   verbatim (trimmed); an empty value means "keep the existing number" (never blanks it). The server is the
   authority — the client never generates a number.
4. `reservationNumber` is **unique** among reservations (partial unique index, NULL allowed). A create/update
   that would collide with another reservation's number is rejected with HTTP 400 (`RESERVATION_NUMBER_TAKEN`).
5. **Devis → reservation conversion**: when an existing row's `kind` becomes `'reservation'` and it has no
   `reservationNumber` yet, one is generated at that moment. The `devisNumber` (if any) is preserved untouched.
6. **Existing reservations are backfilled** once (idempotent migration): every `kind = 'reservation'` row
   lacking a number receives one, grouped by the month of its `createdAt`, sequential within the month ordered
   by `createdAt` then `id`. No existing number is overwritten.
7. Devis keep their `devisNumber` exactly as today — this feature does not touch devis numbering.

### Search

8. A search matches `kind = 'reservation'` rows by, case-insensitively, ANY of:
   `reservationNumber`, `firstName`, `lastName`, `firstName || ' ' || lastName`,
   `lastName || ' ' || firstName`, `email` — each as a substring (`LIKE %q%`).
   _(Updated 2026-10-27: the search also matches `kind = 'cancelled'` rows — search is the one path that
   must still find a cancelled stay, per `specs/payment-schedule-and-cancellation.md` §3.5 rule 26. Code:
   `reservationsModel.search()`.)_
9. Search results are **shaped server-side** (fat backend): `{ id, reservationNumber, clientFullName,
   propertyName, startDate, endDate, status }`, ordered by `startDate DESC`, capped at 20 rows.
   _(Updated 2026-10-27: there is no `status` field. The shape is `{ id, reservationNumber, clientFullName,
   propertyName, startDate, endDate, cancelled, cancelledAt }` — `cancelled` is `kind === 'cancelled'`,
   `cancelledAt` the cancellation timestamp or `null` — ordered by `startDate DESC, id DESC`.)_
10. The search is **live**: the client queries the server as the operator types (debounced ~250 ms); the
    dropdown updates on each response. Selecting a result navigates to the reservation fiche
    (`/reservations/:id`).
    > **Sans test** — no unit test: the behaviour is browser interaction (debounce, dropdown, navigation),
    > pinned end to end by the Playwright suite `e2e/specs/reservations/reservation-search.spec.js` (the
    > five query forms, and a selected result opening its fiche), which the coverage script does not read.
    > Declared at the 2026-10-27 spec review when the Status moved to `Implemented`.
11. An empty/blank query returns no rows (the box shows a hint, not the whole table).

### Number on the guest emails

12. _(Updated 2026-10-27: the shipped J-7 / J-2 copy no longer carries the line. The guest-email
    sequence rewrite ([guest-email-sequence.md](guest-email-sequence.md) §6.1, neutral copy of
    plugins-phase-p rule 13) moved the recall to the **Confirmation** email
    (`server/src/utils/guestEmailSequenceTemplates.js` `CONFIRMATION_BODY`); the deposit reminder also
    carries it (`utils/defaultEmailTemplatesRegistry.js`), and
    `server/src/tests/default-email-templates-registry.unit.test.js` asserts the J-2 has **no** number
    recap. The 2026-06 content migration in `database.js` still injects the line into a stored J-7 / J-2
    whose recap header matches the original anchor. The token and its gate are unchanged.)_
    The J-7 (`arrival_reminder_7d`) and J-2 (`arrival_reminder_1d`) reminder emails recall the number in
    the stay recap, via a new `{{reservationNumber}}` token gated by `{{#if hasReservationNumber}}` (the
    line is omitted when a reservation has no number yet — e.g. a freshly-imported iCal booking before the
    number is assigned). Every reservation receives a number (manual create, devis→reservation conversion,
    iCal import, and the one-shot backfill), so the line shows in practice.

**Edge cases:**
- Two reservations created the same month → `…-001`, `…-002`. Next month resets to `…-001`.
- Operator overrides a number to one already used by another reservation → 400, the fiche shows the error,
  nothing is saved.
- Operator clears the number field and saves → the previous number is kept (no blanking, no regeneration).
- A devis (not yet a reservation) does not appear in search results and shows no reservation number on its fiche.
- Backfill on a DB where some reservations already have a number (e.g. partial prior run) → only the
  numberless ones are filled; idempotent across boots (migrations-table guard).
- Query matches a number fragment (`202606`) → all that month's reservations list (capped at 20).
- Accent sensitivity: matching uses SQLite `LOWER` + `LIKE` (ASCII-case-insensitive), mirroring the existing
  `/emails/eligible-reservations` search. Accent-insensitive matching is out of scope (see §8).

### Numbering after a cancellation (2026-10-18)

> **Why this was added.** A cancelled stay keeps its number (`kind = 'cancelled'`) and the unique index
> covers it, but the generator only scanned `kind = 'reservation'`. Once the latest number of the month
> belonged to a cancelled stay, every creation reused it: HTTP 500 on the fiche, on the devis conversion
> and on the iCal import, until the month changed. The failed fiche creation also left its row behind,
> without a number, blocking the dates and exported in the iCal feed.

13. The next number is computed over **every row that carries a number**, whatever its `kind` (a cancelled
    stay included), and the counter max is **numeric** (the all-digit suffix after `AAAAMM`; a value of
    another shape is ignored). A reservation creation — the row, its number, its history entry, its option,
    night and resource lines — is **one transaction**: a failure anywhere rolls the whole write back, so no
    stay is ever left half-written or without a number. The devis conversion and the iCal import were
    already transactional; they share the generator and therefore the fix.
14. A **one-shot repair** at boot (`reservation_number_repair_numberless_v1`) gives a number to every
    `kind = 'reservation'` row still lacking one, in the month of its `createdAt`, writes a history line on
    it (« N° de réservation → `AAAAMM###` (attribué par réparation) ») and lists each one in the boot log.
    Nothing is deleted: a ghost left by the old failure cannot be told from a real stay by the data, so the
    operator decides. Idempotent.
15. **A repaired stay stays on the dashboard until checked (2026-10-18).** The repair of rule 14 also
    stamps `numberRepairedAt` on each stay it numbers. The dashboard card « À vérifier — N réservation(s)
    restée(s) sans numéro » (`RepairedReservationNumbersAlert`, admin only) lists them — number, client,
    lodging, dates — each row opening the fiche, with « Vu » clearing the stamp
    (`POST /dashboard/repaired-reservation-numbers/:id/acknowledge`). The number is kept; a stay found to
    be a ghost is cancelled from its fiche like any other. *Why: the second review of 2026-10-18 noted
    that the boot log is the only place rule 14 reported its repairs, that the operator never reads it,
    and that a ghost keeps blocking its dates and leaves in the iCal export.*
16. **Fixed at the 2026-10-27 spec review — the « taken » check matches the index.** The unique
    index on `reservationNumber` covers every row, but `isReservationNumberTaken` only looked at
    `kind = 'reservation'`: a number carried by a devis row passed the check and failed on the index
    instead of answering the French 400 `RESERVATION_NUMBER_TAKEN`. The check now covers every row
    (cancelled stays were already refused: they keep `kind = 'reservation'`).

17. **The search says when it is unavailable, and is the administrator's alone (audit R4, 2026-10-29).**
    When `GET /api/reservations/search` fails, the dropdown reads « Recherche indisponible. » in place of
    « Aucune réservation », which would read as « this reservation does not exist »; the next answer
    clears it. The server allowlist refuses the search to reception and accountant (the reception rule
    11, which neither role can follow to a fiche anyway), so the top-bar box and the phone's search
    icon are rendered for an administrator only.
    Tests: `ReservationSearchBox.failure.test.jsx`, `App.role-confinement.test.jsx`.

## 4. Architecture

> **Fat backend, thin frontend.** Number generation, uniqueness validation, backfill, and search matching +
> result shaping all live on the server. The client renders the (read-mostly) number field and an Autocomplete
> dropdown, and navigates on select — no client-side generation, matching, or filtering.

## 5. Data model

- **`reservations.reservationNumber`** — new `TEXT` column, NULL allowed (devis stay NULL).
- **Index** — partial unique: `CREATE UNIQUE INDEX IF NOT EXISTS ux_reservations_reservationNumber ON
  reservations(reservationNumber) WHERE reservationNumber IS NOT NULL` (mirrors the devisNumber index).

**Migration strategy (idempotent, in `database.js`):**
1. `ALTER TABLE reservations ADD COLUMN reservationNumber TEXT` guarded by a `PRAGMA table_info` check
   (existing pattern in this file).
2. Create the partial unique index (`IF NOT EXISTS`).
3. **Backfill** (run once, `migrations` table key `reservation_number_backfill_v1`): for each
   `kind = 'reservation'` row with NULL/empty `reservationNumber`, ordered by `createdAt, id`, assign
   the per-month running counter `AAAAMM###` (starting after any number already present for that month).
   Wrapped in a transaction.
4. **Drop hyphens** (run once, key `reservation_number_drop_hyphens_v1`): when the format changed from
   `AAAA-MM-###` to `AAAAMM###`, reformat the existing values. The migration matches **only** the original
   shape (SQLite `GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][0-9]'`) and strips the hyphens
   (`REPLACE(..., '-', '')`). Custom / non-conforming numbers are **left untouched**. A row is skipped when
   its de-hyphenated value would collide with an existing number (the partial unique index stays satisfied).
   Idempotent.

5. **Repair numberless stays** (run once, key `reservation_number_repair_numberless_v1`, 2026-10-18 — rule 14;
   preceded by `ALTER TABLE reservations ADD COLUMN numberRepairedAt TEXT`, guarded, rule 15):
   number every `kind = 'reservation'` row still without one, add a history line, log each id. Never deletes.

**Data impact:** additive column; no existing data lost. Backfill only writes NULL/empty rows; the
drop-hyphens migration only rewrites original-format `reservationNumber` values (never devis, never custom
numbers, never a value that would collide). Devis rows are never touched.

## 6. UI / UX

### Reservation fiche — number field (`StaySection`)

- A **"Numéro de réservation"** TextField near the top of the Stay section (after the property select).
  Pre-filled with the generated number; editable. Helper text: *« Modifiable »* — until 2026-10-18 it
  read *« Généré automatiquement — modifiable »*, which was false on a fiche whose number an intake had
  replaced by the platform's own (review 2026-10-18, n4).
- On save collision → the server returns 400 `RESERVATION_NUMBER_TAKEN` with the message *« Ce numéro est
  déjà utilisé par une autre réservation. »*, surfaced through the fiche's **standard save-error dialog**
  (the same `alert()` path as the min-nights / capacity / gross errors — consistent with the page, no
  bespoke inline field state). The fiche stays open, nothing saved.
- New (unsaved) reservation: the field is empty with helper *« Attribué automatiquement à l'enregistrement »*
  until the first save; the number is generated server-side and shows when the fiche is reopened.
- Devis fiche: the field is **hidden** (`isDevisMode`) — devis use `devisNumber`, unchanged.

### Number recall in the J-7 / J-2 emails

- The stay recap of both reminder emails gains a line *« - N° de réservation : 202606001 »* (gated by
  `{{#if hasReservationNumber}}`). No new UI; the operator sees it in the email preview/editor like any
  other recap line. Existing installs are upgraded by an idempotent content migration (the seed is
  insert-only and the J-2 force-overwrite already ran). _(Updated 2026-10-27: the example used the
  original `AAAA-MM-###` format, dropped on 2026-06-19.)_ _(Updated 2026-10-28: the migration writes a
  template only when it lacks the token and still carries the anchor, so an operator-edited reminder keeps its
  « last modified » date across boots.)_

### Search box (`ReservationSearchBox`) — global, in the top bar (2026-06-19)

- A single-line Autocomplete with a search icon and placeholder *« Rechercher une réservation (n°, nom,
  prénom, email)… »*, mounted in the top `AppBar` next to the « GuestFlow » wordmark, so it's reachable from **every**
  page (was previously duplicated on Calendrier + Dashboard).
- As the operator types (≥1 char, debounced 250 ms), the dropdown lists up to 20 matches, each rendered as:
  **`N° · Nom Prénom · Logement · 10 → 13 juil. 2026`**. `noOptionsText` = *« Aucune réservation »*; while
  fetching, *« Recherche… »*.
- Selecting a row navigates to `/reservations/:id` (with `?from=<current location>` for the back affordance).
  The box clears after navigation; on mobile the expanded field collapses again.

### Responsive

- **Number field:** full-width on `xs`, sits in the existing StaySection grid on `md+` (no new breakpoints).
- **Search box (header):** on `md+` the field is always visible next to the logo (`maxWidth: 440`). On
  `< md` the header would be too tight (burger + wordmark), so the field collapses behind a **magnifier
  `IconButton`**; tapping it expands a **full-width** field over the toolbar with a close (`×`) button.
  Touch targets ≥44px. No horizontal scroll on `xs`.
- The fiche keeps its existing `PageActionBar` (Save/Cancel/Delete) — no new page-level action. The search box
  is now a header element, present on every page, not page content.
