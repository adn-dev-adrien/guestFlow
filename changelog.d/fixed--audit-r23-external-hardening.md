- **Qonto: a new consent subscribes the webhook on the account it names** (`settings-one-save-and-automatic-webhook.md` rule 10, audit R23 E23-1). After a switch to production, or a consent on another organisation, the old account's record answered « skipped » and no webhook ever arrived on the new one: paid links were seen only on the return page or at the poll. A successful authorisation now forgets the record, then lists, adopts or creates. An instance that switched before this version needs one new consent.
- **Qonto: two webhook checks at once share one call** (same spec, rule 8, E23-5), so they can no longer create two subscriptions.
- **Qonto: a token refresh overtaken by new credentials or a new consent stores nothing** (`qonto-settings-in-app.md` rule 19, E23-4).
- **Qonto: a host variable that does not name Qonto always wins** (`qonto-settings-in-app.md` rule 5, reading of 2026-11-05). A loopback fake or dead port held only until an environment was stored. A variable naming a real Qonto host still gives way to the chosen environment. Under `npm test`, a dial to a real Qonto host is now refused and fails the file (`server-test-isolation.md` rule 14).
- **iCal and push: reserved addresses are not public** (`ical-import-hardening.md` rule 17, E23-6, R23-I7): the benchmark, documentation and special-purpose IPv4 ranges, and any IPv6 outside global unicast.
- **Push: a name is judged where it is dialled** (`pwa-push-notifications.md` rule 15, E23-7): a name answering a private address opens no connection, counts as failed and keeps its row.
