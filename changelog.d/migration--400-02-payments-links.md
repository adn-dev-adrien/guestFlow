- **After the update: open payment links lapse 36 hours after the first boot; links on taken dates and orphan links are withdrawn without any guest e-mail.** Check the boot lines `[migration:dates-taken-links]`, `[migration:orphan-links]`, `[migration:link-validity]` and `[migration:link-valid-until]`.
- `payment_links` keeps `qontoPaymentLinkId` / `qontoPaymentId` next to the neutral `providerLinkId` / `providerPaymentId` (copied on upgrade, kept equal by triggers, so a rollback keeps links working), and gains `provider` ('qonto' for every existing row), `remoteCancelPendingAt`, `cancelReason`, `lastLookAt`, `deactivationAlertedAt`, `takenByReservationId`, `unpaidReadAt`, `noticeJudgedAt`, `withdrawnAt`, `noticeClosedReason`, `basketJson` and `installmentId`. Nothing is lost.
- `orphan_payment_links_withdrawn_v1`: every `open` link whose stay row is missing becomes `cancelled` / `orphan` with the deactivation owed, one `[migration:orphan-links]` log line per link. No network call at boot: the first poll pass reads each link's payment, then deactivates it (or sends the orphan alert if it was paid meanwhile); paid, cancelled and expired links are untouched. With the provider not connected the link stays listed in « À traiter » (« Liens de paiement encore actifs »).
- `payment_link_validity_backfill_v1`: every `open` link (Qonto's `0001-01-01…` sentinel and complement links included, one `[migration:link-validity]` line each) gets `expiresAt` = install + 36 h, then lapses like any link; re-send the requests still wanted.
- `dates_taken_links_withdrawn_v1`: open links of an unpaid devis or reservation whose nights another stay already holds are withdrawn once (`cancelReason = 'dates-taken'`, one `[migration:dates-taken-links]` line per link, no network call at boot; the first poll reads each payment and books a link paid meanwhile in date conflict), without telling the guest; paid rows are untouched. `dates_taken_notice_backlog_v1`: stays already holding such a link get a « Dates prises » row `not-sent` / `upgrade` (never a guest e-mail; `dates_taken_notices` is a new table, rebuilt once to allow the `sending` status, rows and ids kept); the template `dates_unavailable_notice` is seeded (Manual) and re-anchored to `datesTaken` (`dates_unavailable_notice_anchor_v1`).
- `payment_link_valid_until_sentence_v1` / `_v2`: the default payment e-mails (deposit, balance, full, installment requests, acompte reminder) gain « Ce lien est valable jusqu'au … » in a conditional block, on templates nobody edited (v1: a template still holding, to the character, a shipped default text; v2: recognised by SHA-256); an edited template keeps its text and is named in the boot line `[migration:link-valid-until] …; edited, left as they are: …`. No send mode changes (every template stays Manual); after a rollback the earlier release drops the line instead of printing « valable jusqu'au . ». `installment_template_anchor_v1` moves the installment request from `start` to `installmentDueDate`.
- `cancellation_notice_kept_sum_v1` and `cancellation_notice_neutral_opening_v1` reword only the exact seeded sentences of the stored `cancellation_notice` (French and English); a body the operator reworded, the send mode and the enabled flag are left alone.
- `bank_reconciliation_lines.auto` (0) and `groupId` (NULL) (`plugin:online-payment:reconciliation_v2`): existing lines count as confirmed by the operator.
