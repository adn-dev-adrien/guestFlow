Plugins — phase 1 : le contrat des plugins, et cinq plugins sortis du cœur

Spec à valider · 28 septembre 2026 · référence : specs/plugins-phase-1-sdk.md · branche feature/plugins-phase-1 → inte/plugins

Le constat

La phase 0 a donné un interrupteur aux 12 plugins, mais leur code vit toujours dans le cœur. Le cœur les connaît par leur nom : il crée leurs tables et garde leurs réglages dans ses propres colonnes. Il lance aussi leurs tâches et les appelle à la main après chaque écriture de réservation. Chaque garde de la phase 0 a été posée à la main, appel par appel.

Ce que la cartographie a mesuré

  • Météo : 463 lignes serveur, 1 table, 1 clé chiffrée, aucune tâche planifiée.
  • Vacances scolaires : 2 tables et 11 périodes insérées en dur. Il y a aussi une tâche horaire, et des pastilles dans 3 calendriers.
  • Google Agenda : 8 colonnes de réglages, dont 2 chiffrées. Surtout, 10 appels directs éparpillés après les écritures de réservation.
  • Recettes : 3 routes nichées dans celles des logements et une tâche quotidienne.
  • Portail Sowel : 1 084 lignes, 4 chemins d'e-mail, le sas, la fiche et le tableau de bord.
Quatre fuites côté serveur, sur le portail. Même désactivé, le serveur continue de :
  • servir l'alerte des clés du tableau de bord ;
  • renvoyer les champs du portail dans les données du sas ;
  • calculer les variables du portail dans les e-mails ;
  • créer les clés du connecteur à chaque démarrage.
L'écran cache tout, le serveur non. Sortir le plugin du cœur les ferme par construction.

Ce qu'on propose

On inverse le sens. Le cœur offre des points d'extension, et chaque plugin s'y inscrit. Le cœur ne connaît plus qu'une liste de modules.

Garde-fou : un test parcourt les imports. Il échoue si le cœur importe un plugin, ou si un plugin importe le cœur autrement que par le SDK. C'est ce qui rendra mécanique la sortie en paquets de la phase 4.

Essaie : désinstaller avec ou sans effacement

Seuls les 5 plugins sortis du cœur proposent l'effacement. Les 7 autres ont encore leurs données dans le cœur et gardent le comportement de la phase 0 ; « Linge » est là pour le montrer. Clique sur un nom pour ouvrir son détail.

Essaie : les événements remplacent les appels à la main

Choisis une action sur une réservation, puis active ou désactive Google Agenda. Le cœur émet l'événement ; seul un plugin actif le reçoit, après la réponse, sans jamais la ralentir ni la faire échouer.

Action

Essaie : le code portail appartient au sas, pas à Sowel

Le code du clavier du portail est une information d'arrivée. En phase 0, il était caché dès que le plugin Sowel était désactivé. Désormais, l'étape « Portail » du sas s'affiche si le code est renseigné ou si Sowel a une clé pour ce séjour. Le QR de Sowel vient s'ajouter dans l'étape.

Ce qui change pour Solio

  • Rien de visible. Les tables existent déjà : les migrations des plugins ne trouvent rien à faire. La clé Météo et la connexion Google sont recopiées octet pour octet dans la nouvelle table des réglages. Les anciennes colonnes restent en place une version, pour qu'un retour à la v3.5 retrouve tout.
  • Le message après la connexion Google revient. Aujourd'hui, la redirection perd le paramètre qui le porte. Je le vérifie dans le navigateur avant de corriger.
  • Un nouveau client n'a plus aucune table ni aucune clé de connecteur pour ces 5 plugins tant qu'il ne les installe pas. Les 11 périodes de vacances 2024-2026 codées en dur disparaissent. À l'installation, le plugin synchronise tout de suite 24 mois depuis education.gouv.

Ce qu'on ne fait pas dans cette phase

  • Les 7 autres plugins (sas, linge, ressources à l'heure, site, Neat, Qonto, export comptable) → phases 2 et 3.
  • Le téléchargement de plugins depuis un registre signé → phase 4.
  • La suppression des anciennes colonnes de réglages → une version plus tard.
  • La rotation des clés du connecteur Sowel à l'effacement.
  • Le cloisonnement des plugins : ils tournent dans le même process, avec accès complet à la base.
  • La console de gestion des clients (abonnements, déprovisionnement, alertes d'échéance, relances de paiement) : c'est un chantier à part, noté au §14 de l'étude. Il aura sa propre spec avant tout code d'hébergement.

Les risques

RisqueParade
Une grosse PR : des dizaines de fichiers déplacésLes tests existants suivent leur code avec des assertions inchangées, et on compare le nombre de cas avant et après. La suite E2E complète tourne sans modification : elle prouve que rien de visible n'a bougé.
La connexion Google perdue lors de la recopie des réglagesCopie octet pour octet avec la même clé de chiffrement, anciennes colonnes conservées, et vérification sur un shadow de Solio avant le merge.
Un des 10 appels directs oublié en passant aux événementsUn test par ancien point d'appel. Le rattrapage Google toutes les 15 minutes reste en filet, comme aujourd'hui.
Un effacement de recettes qui toucherait aux prixL'effacement ne retire que le rattachement à la recette : les saisons, les prix et les fermetures restent, les saisons devenant « Manuelle ». Un test le vérifie. L'argent ne bouge jamais.

Tranché

  • P1 — le code va dans server/src/plugins/<id> et client/src/plugins/<id>.
  • P2 — une seule PR, vers inte/plugins.
  • P3 — une table de réglages par plugin (plugin_settings).
  • P4 — « Effacer aussi ses données » dès maintenant pour les 5 plugins sortis du cœur.
