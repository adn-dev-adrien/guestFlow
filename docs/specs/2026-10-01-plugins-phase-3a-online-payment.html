Plugins — phase 3a : le paiement en ligne sort du cœur

Spec specs/plugins-phase-3a-online-payment.md · 1er octobre 2026 · première des trois PR de la phase 3 (3b Neat, 3c bain à l’heure)

Le constat

Le paiement en ligne est le seul plugin qui encaisse de l’argent. Son code est encore dans le cœur, et il est écrit pour Qonto à chaque ligne. La cartographie a trouvé trois défauts, que tu as choisi de corriger dans cette PR :

1 · « Relancer » sans plugin

Le bouton du tableau de bord crée un lien Qonto même quand le paiement en ligne est éteint.

2 · Deux façons d’enregistrer un paiement

Un paiement reçu par Qonto coche « acompte payé » directement. Il saute la répartition du montant entre les lignes du séjour, que la comptabilité lit. Cocher le même acompte à la main la fait.

3 · Des liens abandonnés encore payables

Annuler un séjour, ou remplacer un lien dont le montant a changé, ferme le lien dans GuestFlow seulement. Chez Qonto il reste payable, et personne ne le voit.

Ce qui ne doit pas bouger

Les adresses enregistrées chez Qonto (webhook, retour OAuth), les réponses lues par le site WordPress, les liens déjà envoyés, la console qui réutilise le module Qonto.

Ce qu’on propose

  • Le cœur garde le chemin de l’argent : demander un montant, enregistrer ce qui est payé, confirmer le séjour. Il parle à un fournisseur de paiement par une petite interface : créer un lien, lire s’il est payé, le désactiver.
  • Qonto devient ce fournisseur, dans le plugin « Paiement en ligne » : connexion, webhook, réglages, vérification de rattrapage (toutes les 8 heures, comme aujourd’hui).
  • Une seule fonction enregistre un paiement, qu’il soit coché à la main ou reçu en ligne.
  • Chaque lien abandonné est désactivé chez Qonto. Si Qonto ne répond pas, GuestFlow réessaie à chaque vérification et te prévient.
  • « Adresse du site public » passe dans Paramètres › Conditions générales, car c’est le cœur qui s’en sert pour le lien des CGV dans les emails.

Ce qu’on ne fait pas

  • Neat (3b) et le bain à l’heure (3c).
  • Un deuxième fournisseur (Stripe…) : l’interface le permet, aucun n’est écrit.
  • Un registre des paiements : un paiement reste une case cochée sur le séjour plus la ligne du lien.
  • Rembourser chez Qonto un paiement reçu sur un lien annulé : GuestFlow te prévient, tu rembourses à la main.

Les risques

  • La migration renomme deux colonnes de payment_links. Les liens ouverts de Solio doivent rester retrouvables : un test rejoue la mise à jour sur une base v3.8, la copie de la base de dev aussi.
  • La désactivation chez Qonto n’a jamais tourné côté instance. Elle est testée en unitaire. Pour la voir pour de vrai, il me faut ta connexion sandbox Qonto sur l’instance de test (Q1).
  • La console réutilise le module Qonto : ses imports suivent les fichiers déplacés, et ses suites tournent en CI.
