Plugins — phase 4 : paquets, registre signé, mises à jour

Spec specs/plugins-phase-4-registry.md · 08/10/2026 · branche feature/plugins-phase-4 → inte/plugins · implémentée, arbitrages P23–P27 pris avec l’option recommandée
En une phrase. Chaque plugin devient un paquet avec sa propre version ; une release les embarque tous, la console peut en publier de nouvelles versions entre deux releases, et la page Plugins les installe, les met à jour et revient en arrière. Solio ne voit aucune différence tant qu’aucun registre n’est configuré.

Constat

Avant la phase 4

  • Les douze plugins sont compilés dans le cœur : listes d’imports statiques côté serveur et client.
  • Le catalogue est une constante figée ; pas de version, pas de dépendances, pas de plage de compatibilité.
  • La release publie une seule archive ; rien par plugin.
  • Un plugin non installé est quand même chargé et téléchargé par le navigateur.

Ce qui bloquait la suite

  • Corriger un plugin imposait une release complète du cœur.
  • Le dépôt devient privé (D4) : une instance ne peut plus lire GitHub sans jeton.
  • La console a déjà une clé Ed25519 et chaque instance sait vérifier ses signatures.

Ce qu’on propose

Le paquet

  • <id>-<version>.tgz : manifest.json, server/ (sans tests ni node_modules), client/ (un module ES et ses morceaux).
  • Le manifeste décrit le plugin : nom, version, plage GuestFlow, plage SDK, dépendances, journal des versions.
  • Le SDK a sa version (1.0.0). Le build refuse tout import hors du dossier du plugin et du SDK.
  • Côté navigateur, React, MUI, le routeur et le SDK sont ceux de l’application : un seul thème.

Le registre et l’instance

  • Page « Registre » de la console : dépôt de paquets, retrait d’une version ; index signé.
  • L’instance lit l’index au démarrage, toutes les 6 h et sur demande ; signature fausse → index ignoré.
  • Sans registre : les versions de l’archive, et rien ne le signale.
  • Mise à jour : téléchargement, empreinte vérifiée, bascule, redémarrage. Retour arrière possible 7 jours.
  • Une release charge chaque plugin depuis son paquet ; un plugin non installé ne coûte rien.

Ce qu’on ne fait pas

  • Plugins tiers et comptes développeurs : seul le registre officiel existe.
  • Mises à jour poussées sur toute la flotte : c’est la phase H (hébergement).
  • Mise à jour automatique : rien ne s’installe sans un clic de l’administrateur.
  • Un dépôt par plugin : les paquets sont construits depuis ce dépôt.
  • Un nouvel identifiant de plugin publié seul : il arrive avec une release du cœur, qui connaît son forfait.

Risques et parades

Solio après la migration

Les lignes builtin deviennent bundled, actives, données intactes. Vérifié sur une copie de la base de dev : tableau de bord, fiche réservation, planning, page Plugins, Paramètres › Linge, Intégrations, Vacances scolaires, sans erreur console, avec le build de production et les douze paquets.

Une release qui retomberait sur les sources

Le build client ne contient plus de code de plugin. Une instance trouve plugins-dist/ et charge les paquets quel que soit NODE_ENV ; seuls npm run dev et la suite E2E de dev forcent les sources.

Redémarrage

Une mise à jour finit par un arrêt propre que PM2 relance. Sans superviseur, elle est refusée avant tout changement. Une mise à jour qui échoue laisse la version en place.

Registre compromis ou en panne

Index signé par la clé de la console ; empreinte et taille vérifiées ; https seulement. En panne : versions de l’archive et une ligne discrète.

Arbitrages pris pendant l’implémentation

  • Plage GuestFlow des douze manifestes : >=3.9.0 sans plafond ; c’est la plage SDK (^1.0.0) qui protège d’un cœur incompatible.
  • Une mise à jour dont la nouvelle version exige un plugin absent est refusée (« à installer d’abord ») ; seule l’installation propose la dépendance.
  • Après une installation, la page se recharge pour charger le nouveau paquet dans le navigateur ; côté serveur aucun redémarrage.
  • La liste des paquets à charger est lisible avant la connexion : le navigateur les charge avant l’application.
  • Règle 25 ajoutée : un plugin bundled suit la version que la release embarque.
  • Les lignes de journal plugin:<id> sont écrites en français, car lues dans la fenêtre de mise à jour.

Après la relecture du 17/10

  • Un paquet n’embarque plus sa propre copie de MUI : les icônes des plugins prennent le thème Maison ; le build échoue sinon.
  • L’application ne charge que les composants MUI dont les plugins ont besoin ; le code chargé avant le premier affichage reste au niveau d’avant (572 Ko compressés contre 573).
  • L’adresse des fichiers d’un plugin porte l’empreinte du paquet : aucun navigateur ne garde un ancien fichier.
  • Une modification de plugin porte sa nouvelle version et ses lignes de journal dans sa propre PR ; la PR de release ne touche aucun manifeste.
  • « Revenir à la version précédente » demande confirmation ; l’attente du redémarrage s’arrête après 90 s avec « Réessayer ».
  • Une écriture venue d’un autre site est refusée ; un index de registre plus ancien que le dernier lu aussi.
