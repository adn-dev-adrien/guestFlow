Comptes : mot de passe oublié, second code, accès du support — H2

Résumé de la spec specs/hosting-h2-account-security.md (règles 1–17) · 08/10/2026 · données fictives, tout se manipule.

En bref

Le constat
  • Un propriétaire seul qui oublie son mot de passe est bloqué jusqu'à ce qu'on lance reset-admin.js sur son serveur.
  • Les comptes d'une instance n'ont qu'un mot de passe. La console a déjà un second code (TOTP, email, codes de secours).
  • Le support n'a aucun moyen tracé et consenti d'entrer dans l'espace d'un client.
Ce qu'on propose
  • Mot de passe oublié : un lien par email, valable 1 h, à usage unique, même réponse que l'adresse existe ou non, 3 demandes par adresse et 20 par IP par heure.
  • Second code au choix (appli ou email), 10 codes de secours, « faire confiance à cet appareil 30 jours », verrou 15 min après 5 erreurs. Le code TOTP est partagé avec la console (un seul module).
  • Accès du support : la console demande, un administrateur autorise (1 h, 24 h ou 7 j) ou refuse, peut révoquer. Le support entre par un lien signé valable 2 min, sous un compte « Support GuestFlow », barre rouge, chaque écriture et chaque page journalisées.
Ce qu'on ne fait pas
  • Imposer le second code à tout le monde (une carte invite les administrateurs, « Plus tard » la cache 30 jours).
  • Clés d'accès (WebAuthn, passkeys), SSO.
  • Accès du support à une instance auto-hébergée : sans GUESTFLOW_LICENCE_PUBLIC_KEY, rien n'est proposé.
Risques
  • Lien de réinitialisation détourné : il est construit sur l'adresse publique configurée, jamais sur l'en-tête Host de la requête.
  • Téléphone perdu, seul administrateur : codes de secours, sinon reset-admin.js --disable-2fa (inscrit au journal du compte).
  • Lien support rejoué : signé, 2 minutes, usage unique, refusé sans accès ouvert ; l'accès expiré coupe la session à la requête suivante.
  • Les limites de demandes vivent en mémoire : un redémarrage les remet à zéro (acceptable : le lien reste à usage unique et valable 1 h).
