Retirer un plugin sans rien casser

Chaque plugin a été retiré un par un — désactivé, désinstallé, puis son code supprimé — et tout le reste a été vérifié. Ce qui tient, ce qui casse, et la garantie qu’on propose de mettre dans la CI pour que ça reste vrai.

Le constat

15 / 15plugins désactivés puis désinstallés : l’application tient
40pages vérifiées à chaque retrait, fiches avec données comprises
16 / 16plugins dont le code absent empêche le serveur de démarrer
40fichiers de tests du cœur qui importent un plugin

Ce qui tient

  • Sur une copie des données réelles, en build de production : désactiver, désinstaller (après redémarrage, le plugin n’est plus chargé), réinstaller. Aucune erreur de page, aucune erreur serveur, les données reviennent.
  • Les garde-fous font leur travail : le paiement en ligne refuse de partir avec 5 liens ouverts, l’Accueil et le Comptable refusent de partir avec un compte qui en dépend.

Ce qui casse

  • Le serveur ne démarre pas si le dossier d’un plugin manque : le catalogue lit chaque manifest.json au chargement.
  • Les tests ne survivent pas au retrait : 40 fichiers du cœur, 4 tests de plugins qui en importent un autre, et les tests du moteur de plugins écrits sur de vrais plugins (« seize plugins »).
  • En mode développement, un plugin inscrit en base mais sans code compte comme actif.
  • Latent : un rappel d’acompte peut renvoyer un lien Qonto alors que le paiement en ligne ne tourne plus.

Plugin par plugin

Choisir un plugin : ce qui dépend de lui, et ce qu’a donné chaque façon de le retirer.

Ce qu’on propose

1. Les corrections

  • Le catalogue ignore un plugin dont le code manque, au lieu de planter. S’il était installé, il apparaît « Paquet introuvable » sur la page Plugins, désinstallable.
  • Sans module chargé, un plugin n’est jamais actif, en production comme en développement.
  • Les tests du cœur n’importent plus aucun plugin : déplacés dans le plugin, ou réécrits sur un plugin factice. Un test qui prouve une vraie collaboration (le SAS et ses étapes, Neat sur le site) le déclare et se saute quand l’un manque.
  • Le lien de paiement n’est proposé dans un mail que si le paiement en ligne tourne.

2. La garantie, chaque nuit et à la demande

  • Une case par plugin : on supprime son code, puis tests serveur, build, démarrage en production sur une base qui contient encore ses données, contrat des API du cœur, et les pages principales sur ordinateur et téléphone.
  • Un balayage : sur un seul serveur, chaque plugin est désactivé, réactivé, désinstallé, purgé, réinstallé — et ses données doivent revenir à l’identique.
  • Une fiche qui porte les données d’un plugin retiré s’ouvre et s’enregistre sans changer un centime.

La matrice se remplit seule

La liste des cases n’est écrite nulle part : elle vient des dossiers. Ajouter un plugin ajoute sa case — et un test unitaire (celui-là bloque la PR) échoue tant que ses données de test manquent.

Ce qu’on ne fait pas

  • Retirer deux plugins à la fois dans toutes les combinaisons. « Tous retirés » est déjà prouvé par la suite « installation vierge » ; un plugin requis par un autre est retiré avec lui (Site internet emporte Google Vacation Rentals).
  • Ce que voient les consommateurs extérieurs d’un plugin retiré : le site WordPress sans « Site internet », la maison sans « Accès portail », le script de saisie Booking. Ils reçoivent aujourd’hui une réponse « plugin inactif » ; ce qu’ils en affichent relève de leur propre spec.
  • Réécrire les identifiants de plugins cités dans le cœur (prix à l’heure, rôles, modèles de mails) : tous sont conditionnés à « plugin actif », et la matrice prouve qu’ils sont sans effet en son absence.
  • La suite de tests client dans chaque case : un contrôle statique (aucun fichier du cœur n’importe un plugin) et le rendu des pages sans le plugin la remplacent, pour 7 minutes de moins par case.

Le risque

Le chantier des tests

Une quarantaine de fichiers de tests à déplacer ou réécrire, sans perdre un seul cas. Le nombre de tests de chaque suite est comparé avant et après : un cas qui disparaît se voit.

Le temps de CI

Les 16 cases ne tournent plus sur les PR : chaque nuit et à la demande (onglet Actions), 8 en parallèle, une case sous 12 minutes. Aucun contrôle de PR n’attend derrière elles — en échange, la casse d’un plugin se découvre le lendemain du merge, par une issue ouverte automatiquement.
